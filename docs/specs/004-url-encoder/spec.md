状态：M1-04 / Specify + Plan，2026-10-10；待人工审批，未授权编码。前置：002 与 003 已报告 Dev Done，Release Ready 遗留继续保留，不在本规格中关闭。依据：[产品需求](../../product/requirements.md) P1-05～08、[架构](../../architecture/frontend.md)、[决策](../../architecture/decisions.md)、[双层门禁](../../quality/gates.md)、[002](../002-text-statistics/tasks.md)、[003](../003-json-formatter/tasks.md)。

## 目标、范围与现状

在浏览器本地对文本做一次 URI 编码或解码，显式选择 URI 组件/完整 URI 模式，显示结果并允许复制、清空和空输入填示例。支持中文、Emoji、特殊字符、桌面和手机。默认模式提议为 URI 组件，默认无结果；编码/解码使用两个按钮手动触发。

不含表单编解码模式、URL 结构解析/有效性验证、查询参数编辑、自动反复解码、自动检测模式、结果覆盖输入、访问结果地址、链接预览、文件导入、持久化、账户、后端或第三方服务。不对域名进行 IDNA/Punycode 转换。名称中的“URL”不表示输出必然是可访问或可信地址。

当前首页通过真实锚点和展开/收起按钮试用文本统计及 JSON；URL 元数据仍是 planned。本轮仅设计，不改变卡片可用状态。未来正式路径预留 /developer/url-encoder；无路由依赖时不得伪造 History/hash 路由。

## 模式、保留字符与原生语义

| 模式 | 编码 | 解码 | 使用说明 |
| --- | --- | --- | --- |
| URI 组件（默认提案） | encodeURIComponent | decodeURIComponent | 单个路径片段或参数值；会编码结构分隔符；不能把整条URL编码后当原地址 |
| 完整 URI | encodeURI | decodeURI | 保留URI结构分隔符；不会保护参数值中已有的 &、=、#；不等于解析/验证或安全清洗URL |

编码共用原样保留集合为 ASCII A～Z、a～z、0～9，以及 `- _ . ! ~ * ' ( )`。完整 URI 编码额外保留 `; / ? : @ & = + $ , #`；组件编码对它们产生百分号转义。方括号在两种编码中均转义。百分号不在保留集合，原文 `%2F` 编码为 `%252F`；不识别已有转义为“无需编码”。新生成十六进制使用大写。

解码按百分号字节和 UTF-8 解释，接受大小写十六进制。组件解码还原所有有效转义；完整 URI 解码保留表示 `; / ? : @ & = + $ , #` 的百分号转义，并保留其原大小写，例如 `%2f` 仍是 `%2f`，不是 `/`。两种解码都可把 `%25` 解成 `%`、`%20` 解成空格。原本未转义的字符原样保留。语义依据 [ECMAScript URI 操作](https://tc39.es/ecma262/multipage/global-object.html#sec-uri-handling-functions)，不额外套用 RFC 3986 严格转义规则。

空格编码为 `%20`；原文加号在组件编码变 `%2B`、完整 URI 编码保留 `+`；解码原文 `+` 两种都保持 `+`，绝不先换成空格。`application/x-www-form-urlencoded`/URLSearchParams 的空格加号语义是另一种协议，本工具不实现。提示用户：表单中的 `a+b` 不会在此自动解成 `a b`。全角空格、NBSP 和换行均按各自码点处理，不 trim、不转换为ASCII空格。

每次仅处理当前输入一次，不把结果写回输入，不自动识别多重编码：组件编码 `%` → `%25`；手动把结果作为新输入再次编码 → `%2525`。组件解码 `%252F` → `%2F`，再次手动作为输入才变 `/`；完整 URI 模式第二次仍保留 `%2F`。重复点击而不改输入产生相同输出，不累计层数。

### Unicode、错误与空值

- 中文及合法代理对 Emoji 编码为UTF-8百分号序列；不进行 NFC/NFKC，不使用 escape/unescape、btoa/atob 或自动修复字符。
- 编码遇到任意孤立高/低 UTF-16 代理项均拒绝，提示“输入包含孤立的 UTF-16 代理项，无法编码；原文已保留。”不偷偷调用 toWellFormed 替换为 U+FFFD。
- 解码遇到 `%`、`%2`、`%GG` 等非法转义，以及不完整/无效UTF-8（例如 `%E4%BD`、`%C0%AF`、`%ED%A0%80`、`%F4%90%80%80`）整次失败，不返回可复制的部分结果。提示“无法解码：百分号转义或 UTF-8 编码无效；原文已保留。”不显示原生异常消息或声称精确定位。
- 解码原文中没有百分号包裹的孤立代理项，原生API会原样保留；本提案遵循该行为，不将成功描述为Unicode有效性校验。`%ED%A0%80` 是无效UTF-8，须失败，与原样 `\uD800` 不同。页面说明必须明确这一区别；是否统一拒绝原样孤立代理项列为审批事项。
- 空字符串执行操作提示“请输入需要处理的文本”，无结果、复制禁用；纯空白是合法文本：单空格编码 `%20`，解码仍是单空格。按钮可处理空输入以产生明确反馈。
- 换行与控制字符不剥离。纯函数 `%0D%0A` 解码为 CRLF，`%00` 为 U+0000；输入框/只读结果框可能将换行规范化，页面处理以实际输入值为准。复制API使用纯函数结果字符串，手动选区和系统剪贴板可能规范化换行，不承诺原始字节一致。不可见字符不能靠截图判定丢失，测试须核对码元。

## 输入规模与性能（待人工批准）

提议输入上限为100,000 UTF-16码元，按原输入 string.length 检查；与码点数、百分号字节数不同。100000允许，100001超限：保留全部原文、立即清空旧结果/提示，显示中文限额提示，编码/解码禁用；缩短后可手动重试，不自动截断或处理。

按原生算法推导，有效编码结果每个输入UTF-16码元最多产生9个ASCII码元，因此该输入限额下最多900000输出码元；这是空间上界，不是已测性能或额外扩大输入授权。结果不截断，超过资源能力时捕获异常并保留输入。超限检查先于任何编码/解码扫描；不会拿结果长度作为下一轮输入豁免。

发布性能提案：生产构建在 Mac mini M4 及一台记录型号/系统的真实手机，用10k/100k码元ASCII、中文/Emoji混合编码样本及有效百分号解码样本，四种模式/操作组合各连续测10次；纯函数每次≤50ms、按钮触发到结果绘制每次≤200ms。样本不得意外切断代理对/UTF-8转义组，实际长度须登记（可用ASCII补齐）；失败样本另测异常响应。保存每次耗时/最大值/方法局限，不用均值代替。不宣称同步原生API可被超时中断；未达标先评审限制/调度，不自行引入Worker或依赖。Lighthouse90以上仍是初步观察目标，不替代工具时延测量。

## 交互生命周期

复制捕获结果和revision；等待期间阻止第二次复制，但允许编辑/切模式/清空/重新执行/收起。任何失效递增revision，旧resolve/reject只能结束pending，不显示陈旧成功/失败、不选中已失效结果。清空不会提前解除仍在进行的复制锁；卸载后回调不再改UI。刷新/重开默认空输入、空结果、组件模式，不恢复历史、不询问保存。
